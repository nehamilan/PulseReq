<H1>PulseReq — Product Roadmap</H1>

This roadmap is derived from limitations already named in [product_brief.md](docs/Product-Brief.md) — nothing here is a speculative wishlist item invented for this document. Items are grouped by why they're on the list, not by quarter: gaps we already disclosed as real limitations, new capability that extends the same governance pattern already in the product, and things deliberately left out so the roadmap doesn't quietly imply they're coming.

## Closing disclosed gaps (Next)

These fix limitations the brief's guardrails and trade-offs sections already name explicitly. Prioritized first because they reduce real risk in the existing product rather than adding new decision surfaces.
- **Notifications.** Patients and clinicians currently discover state changes — an extension approved, a result released, an embargo about to lapse — only by navigating back to the relevant portal. Named as a gap in the brief's trade-offs section. Lowest-risk item on this list: it doesn't change any decision logic, it just surfaces decisions that already happened.
- **Mobile-responsive patient views.** The Patient Portal currently relies on horizontal scroll at narrow widths — a desktop-first layout. Patients are the most mobile-heavy of the three personas in this product, so this is a real usability gap, not a cosmetic one, and it's prioritized ahead of any other UI work for that reason.
- **A real auth boundary for the clinician's read-only patient-view preview.** Currently a query parameter on the same route as the patient's own view — convenient to build, not a permission boundary. Cheap to fix and worth doing before it's the kind of thing a careful reviewer notices and asks about.

## New capability (Later)

Each of these adds a genuinely new decision surface — who can trigger what, under what bounded conditions — and needs its own scoping (goals, non-goals, controlled vocabulary, guardrails) before it becomes a build prompt, the same way the existing release-policy and extension-governance logic was scoped rather than improvised.
- **Standing / recurring orders.** A clinician authorizes a test to recur on a defined cadence once (e.g. "A1c every 3 months, renewable for 12 months"); the system, not the patient, issues the next requisition when it's due. The patient's role is to book or activate an already-authorized order, never to originate or modify one. Guardrails required before build: scope to a controlled allow-list of test types appropriate for routine monitoring (A1c, lipid panel, TSH, basic metabolic panel — not imaging, not pathology, not anything STAT/urgent); every standing order needs a hard boundary (fixed end date or fixed repeat count) rather than indefinite recurrence, so it can't keep firing after the clinical reason for it has changed; only the authorizing clinician (or another clinician reviewing the chart) can change cadence, extend, or cancel — never the patient. Structurally this reuses the same time-bound, policy-gated pattern already built for result release/embargo, just applied to order issuance instead of order visibility.
- **Result trending.** A view of a lab value across a patient's repeated orders (an A1c trend, say), most valuable for the same test population as standing orders, though it doesn't strictly depend on standing orders existing first — repeat results from ordinary manual reordering already produce trend-worthy data today. The design risk isn't the chart, it's the interaction with release policy: a trend can never plot a point before that individual result has cleared its own release policy. If the most recent value in a series is still embargoed or held for clinician review, the trend either omits that point until it releases or shows the released points plus an explicit "1 result pending release" — it must never silently render a value that hasn't individually cleared the same gate every other result in this app goes through. Reuse the existing per-result visibility rule; don't add a second policy layer for trend visibility specifically. Scope to quantitative lab values with a reference range, and require a minimum number of points (two isn't a trend) before presenting anything as a trend line.
- **Auditor / compliance-officer view.** The audit ledger currently renders but has no dedicated persona who reviews it — named as a gap in the original persona analysis. A real roadmap item: a read-only view scoped to ledger review, not just an unused capability sitting behind the existing portals.
- **EMR ingest.** Receiving orders via a webhook from an EMR instead of the current hand-typed entry — closes the front end of the pipeline the README originally described. This is the one place I'd deliberately introduce a real AI decision into PulseReq, and worth stating as a conscious exception rather than scope creep: an inbound EMR order note is unstructured text, the output space is a controlled LOINC vocabulary, and a clinician confirms before the order issues — exactly the condition under which this portfolio's own decision rule says a model is appropriate, unlike everything else in this product. Everywhere else in PulseReq, rules beat a model; here, the input is genuinely unstructured and the output is genuinely constrained, so the same rule points the other way.
- **LIS egress.** Closing the back end of the pipeline — today PulseReq hands off to the lab and never results a test. Real value, but depends on integrating with a partner lab system rather than something buildable in isolation, so it's a bigger bet than the other items in this group.

## Not planned

Stated explicitly rather than left unmentioned, so this roadmap doesn't imply they're coming later just because they weren't ruled out.
- **Billing and insurance coverage validation** — out of scope; PulseReq models the clinical handoff, not the payment/coverage layer.
- **Multi-clinic / multi-centre routing** for a patient splitting care across providers — a real scenario, but a different product problem than the one PulseReq is scoped to solve.
- **Becoming the system of record for results.** The diagnostic centre's LIS remains the authoritative source; PulseReq stays a coordination layer on top of it, not a replacement for it.
